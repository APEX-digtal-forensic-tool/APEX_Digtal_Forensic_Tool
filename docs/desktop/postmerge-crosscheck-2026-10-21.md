# PR #32 병합 후 전체 재점검 및 교차 검증

- 점검일: 2026-10-21 (UTC)

- 점검 대상: Electron/React 프론트, 로컬 API, 인증 백엔드, MCP, 코어 엔진, AI 정책 및 연결, 패키징

## 결론

기존 자동 검사는 모두 통과했지만, 서로 다른 계층의 입력·출력과 실패 경로를 대조하여 **추가 결함 4종류**를 재현했다. 프론트만의 문제가 아니며, **엔진의 보고서 출처 검증 결함도 1종류 포함**되어 있다. 재현 사례에 대한 수정과 회귀 검사를 추가했다.

검사 통과는 아래 범위의 검증 결과다. 모든 증거 형식·모델·운영체제·실제 사용자 조합에서 오류가 없다는 보증은 아니다.

## 1. 검사 방법

1. 원격 main의 정확한 커밋을 별도 작업 트리에 체크아웃했다. PR #32의 소스 트리와 병합 main의 소스 트리가 동일한 것을 확인했다.
2. 변경 전 전체 Python 시험, 전체 프론트 시험, TypeScript/Vite/Electron 빌드, MCP 릴리스 게이트를 실행했다.
3. 화면에서 만드는 입력 → 로컬 API 모델 → 엔진 서비스 → 저장된 결과를 대조했다. 기존 예제에서 비어 있던 출처 필드에 실제 분석 스냅샷을 넣어 재검증했다.
4. 유효한 시험용 RSA 서명에 잘못된 클레임을 넣어 인증 경계를 확인했다. 서명 위조나 실제 계정 접근은 사용하지 않았다.
5. 새 실패 사례를 테스트로 작성하여 수정 전 실패를 확인했다. 로컬 API 시험 코드의 FileSystemNode 필드명 오타를 먼저 바로잡은 다음, 실제 `422 VALIDATION_ERROR` 실패를 별도로 확인했다.
6. 수정 후 관련 시험, 전체 시험, 정적 검사, 빌드와 별도의 과거 결함 재현 시험 10개를 실행했다.

## 2. 추가 발견 및 수정

### PM-01 — 보고서 새 버전 저장 시 보고서 전체의 출처 정보 유실

**분야:** 프론트 + 로컬 API / **우선순위:** P1 — 포렌식 보고서 추적성

**재현:** 실제 파일을 등록하고 분석 스냅샷을 만든 뒤 그 스냅샷을 참조하는 보고서를 작성했다. 기존 화면과 동일한 입력으로 API에 새 버전을 저장하면 HTTP 200으로 성공하지만, 보고서 전체 `context_snapshot_ids`가 비고 `source_revisions` 개수가 1에서 0으로 줄었다. 섹션 내부의 스냅샷 ID는 그대로여서 겉으로는 출처가 남은 것처럼 보였다. 누락된 필드를 API에 직접 보내도 입력 모델이 받지 않아 422가 발생했다.

**원인:** `ReportVersionDialog`가 섹션 정보만 복사하고 보고서 전체의 다음 정보를 보내지 않았으며, 로컬 `ReportVersion` 입력 모델에도 해당 필드가 없었다.

- `context_snapshot_ids`
- `search_execution_ids`
- `timeline_revisions`
- `ai_assistance_request_ids`
- `ai_result_ids`
- `analyzer_versions`

**수정:** 화면과 API에 이 필드를 함께 연결했다. 기존 섹션의 인용과 새로 수집한 인용도 합쳐 전송하여 보고서 전체 `citation_ids`가 빈 목록으로 바뀌지 않도록 했다. 출처 버전·지문은 클라이언트가 임의로 제공하지 않고 엔진이 검증된 스냅샷으로 다시 산출한다. 예전 화면에서 이미 섹션에만 남긴 스냅샷 ID도 새 버전 작성 시 합쳐서 재검증한다. 과거 저장 버전 자체를 수정하지 않는다.

**검증:** 화면 입력에 여섯 필드가 보존되는지 검사했다. 실제 로컬 API 저장·재조회에서 스냅샷, 출처 지문, 분석기 버전, AI 요청 참조, 기존 인용 ID, 이전 버전 연결이 유지되는지 확인했다. 마지막 교차 검증에서 기존 인용이 없는 예제의 한계를 확인하고 실제 인용을 포함한 경우로 시험을 보강했다. 다른 사건의 스냅샷을 전달하는 요청은 계속 거부되는지 확인했다. AI 요청 참조 생성에는 실제 외부 API 호출이 필요하지 않다.

**기존 데이터 주의:** 이전 결함으로 이미 소실되어 DB에 남지 않은 검색·AI 참조를 자동으로 추정하지 않는다. 섹션에 남아 있는 실제 스냅샷 참조만 새 버전에서 복원·검증할 수 있다.

### PM-02 — 엔진이 보고서 범위 밖 섹션 스냅샷 ID를 수용

**분야:** 코어 엔진 / **우선순위:** P1 — 출처 무결성

**재현:** 정상 보고서 입력의 섹션 `context_snapshot_ids`를 존재하지 않는 ID로 교체해도 새 버전이 저장됐다. 같은 사건의 실제 스냅샷이라도 보고서 전체에는 선언하지 않은 경우, 다른 사건의 스냅샷 ID를 섹션에만 넣은 경우도 거부되지 않았다.

**원인:** 엔진이 보고서 전체에서 검증한 스냅샷 중 섹션 ID와 일치하는 것만 골랐지만, 일치하지 않는 ID의 존재를 오류로 판단하지 않았다. 실제 타 사건 내용이 조회되었다는 의미는 아니며, 검증되지 않은 출처 메타데이터를 저장하는 문제다.

**수정:** 섹션 스냅샷 ID가 사건 검증을 마친 보고서 전체 스냅샷 집합에 속하는지 확인한다. 벗어나면 `REPORT_CITATION_SCOPE_MISMATCH`, target `section.context_snapshot_ids`로 거부하고 버전을 저장하지 않는다.

**검증:** 존재하지 않음, 같은 사건이지만 보고서에 미선언, 다른 사건의 참조를 각각 시험했다. 정상 보고서 작성·검토·승인·내보내기와 MCP/CLI 보고서 흐름도 전체 회귀 시험에 포함했다.

### PM-03 — 오래된 상태의 승인 보고서를 화면에서 내보낼 방법이 없음

**분야:** 프론트 ↔ 로컬 API ↔ 엔진 / **우선순위:** P2 — 사용자 작업 차단

**재현:** 엔진은 `stale_state.is_stale`인 승인 보고서 내보내기에 명시적인 `stale_confirmed=true`를 요구한다. API 필드는 있었지만 화면에는 확인 항목도 전송도 없어 항상 거부됐다. 기존 API 시험이 직접 true를 보내므로 화면의 누락을 잡지 못했다.

**수정:** 해당 상태에서만 필수 확인 체크박스를 표시한다. 기본은 체크 해제이며 사용자가 직접 확인한 경우에만 true를 보낸다. 정상 상태의 보고서는 false를 보내며 엔진의 기존 승인·보관이력·중복 파일 보호를 유지한다.

**검증:** 화면에서 확인 전 폼이 유효하지 않은지, 확인 후 true가 전송되는지, 정상 보고서는 false인지 시험했다. 실제 API에서 미확인 요청 거부 및 파일 미생성, 확인 후 HTML 결과 생성·내용을 확인했다.

### PM-04 — 형식이 잘못되거나 필수 필드가 없는 서명 토큰 처리

**분야:** 인증 백엔드 + MCP 토큰 검증 / **우선순위:** P2 — 인증 계약 및 실패 처리

**재현:** 시험용 키로 올바르게 서명한 토큰에서 다음을 확인했다.

- access의 `exp=null` 또는 배열: TypeError 발생
- access의 `scopes=[1]`: AccessToken 구성 중 ValidationError 발생
- access의 `exp` 누락: 만료 필드 없이 검증 통과
- `allowed_case_ids` 등의 잘못된 타입: 하위 인증 처리까지 전달
- refresh의 `exp`, `session_id`, `sub`, `jti` 누락: decode 통과; 이후 서비스가 필드를 직접 읽으면 예외 가능

이는 서명 검증을 우회하는 공격의 증명이 아니다. 신뢰한 발급자가 계약을 위반한 토큰을 발급하거나 전달했을 때의 처리 결함이다.

**수정:** 기존 RS256·issuer·audience·만료 검증에 필수 클레임과 타입 검사를 더했다. access의 tenant/session/subject/jti, 날짜 정수, 문자열 목록, case_roles 맵과 refresh의 필수 식별자를 검사한다. python-jose가 노출하는 값 변환 오류를 인증 실패로 정규화한다. case_roles 자체가 없는 기존 토큰은 종전과 같이 역할이 필요한 도구에서 별도로 차단한다.

**검증:** 21개의 잘못된 클레임 조합을 직접 시험하고, 실제 ASGI HTTP 경로 4개에서 500 대신 401을 확인했다. 정상 로그인, 갱신, 회전 재사용 감지, 비활성 계정, 로그아웃, JWKS 갱신, MCP 사건별 권한 시험을 함께 실행했다.

**호환성:** 정상 `issue_access_token`/`issue_refresh_token`이 발급하는 토큰 구조는 바뀌지 않는다. 필수 정보가 없는 비정상 토큰은 다시 로그인해 정상 토큰을 발급받아야 한다.

## 5. 남은 실환경 확인

다음 다섯 시험은 이 Linux 실행 환경의 자료/선택 의존성이 없어 skipped 상태다. 성공으로 세지 않았다.

1. 실제 faster-whisper 로컬 모델 + 영어/한국어 음성 정답 자료.
2. 실제 한국어·혼합 OCR 이미지 + Tesseract/tessdata.
3. `pyvhdi` 선택 읽기 백엔드.
4. `qemu-img` 기반 외부 디스크 생성·검증 경로.
5. `pyewf` 선택 E01 읽기 백엔드.

이것이 E01/VHD/VHDX 기능 전체가 미구현이라는 뜻은 아니다. 저장소의 별도 컨테이너 fixture 시험은 전체 시험에 포함되어 있다. 대체 라이브러리와 실제 장비별 경로까지 전부 통과한 것으로 해석하면 안 된다.

출시 전에는 최종 Windows 설치본에서 실제 증거와 필요한 모델을 넣어 기동→분석→보고서 저장까지 확인해야 한다. Windows 패키징 CI 성공은 실제 사용자의 PC와 전체 GUI 수동 검증을 대신하지 않는다. 외부 AI 모델은 API 설정을 받은 뒤 실제 제공자 응답·지연·오류까지 별도로 확인해야 한다.

## 6. 의도된 동작과 비차단 항목

- 비로그인 로컬 분석은 현재 요구사항대로 유지한다.
- 화면의 ‘앱에서 로그아웃’은 앱 메모리 세션 제거라고 명시되어 있다. 서버 전체 세션 철회가 이미 연결됐다고 해석하지 않는다. 서버에는 별도 logout API가 있다.
- 빈 증거 범위의 초안은 유지되지만 보관이력이 없는 승인·내보내기는 엔진이 거부한다. 이를 통과시키기 위해 안전장치를 약화하지 않았다.
- 번들 크기 경고와 passlib의 Python 3.13 관련 crypt 폐기 경고는 남는다. 현재 빌드/시험 실패는 아니며, 이번 결함 수정과 별도로 최적화·의존성 전환을 검토할 수 있다.
- Bandit의 ‘통과’는 기존 분류 정책을 만족했다는 의미다. 미분류 항목 0개이며 기존 medium 분류가 존재하므로 경고 자체가 0개라는 뜻이 아니다.
